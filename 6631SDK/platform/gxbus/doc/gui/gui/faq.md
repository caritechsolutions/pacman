# 编码问题

## 针对GB2312、BIG 5、KSX以及UTF8标准不同而造成的界面实现乱码

可以将UTF8定义为国际标准，那些如GB2312、BIG 5以及KSX这类有某些国家、地区定义的标准为地方标准；

这里按本地化（localization, l10n）与国际化（internationalization, i18n）来作区分，按本地化标准编排的字符集是国际化标准编排的字符集的一个子集，但本地化的子集是不按国际化标准编排的。

所以，在需要支持多个本地化，如同时支持ISO6937、ISO8859-x以及GB2312等标准，或者需要支持除GB2312以外的本地化标准的编码（流或者文件等），将它们能够正常显示在我们的方案界面上，则都使用国际化编码。即UTF8标准编码。即在入口的theme.conf中的encoding设置为utf8（不区分大小写），即将最终的显示都采用它来做。

若某些翻译的XML，如Chinese.xml是按某些本地化的编码标准保存的，如GB2312，那么就需要将其保存为国际化，即UTF8标准。

## 针对文件名显示的乱码问题

bsp.cpp将Language Package选项修改相应配置，如整套方案需要按照本地化的中国大陆GB2312配置的，即打开LANG_SIMP_CHINESE，关闭其他任何选项；如果需要支持中国台湾BIG5编码标准的本地化，即打开LANG_TRAD_CHINESE；如果需要支持韩国国内本体化标准KSX，则打开LANG_KOREAN；如果需要支持日本国内本地化标准JSFS，则打开LANG_JAPANESE；需要国际化UTF-8支持，则打开LANG_US(美式英语)。

一套方案只支持一种编码方式，即任何情况下都按照这一种编码翻译二进制，文件名可以按bsp.cpp里定义的标准读出，而文件内容无法按此标准，也无法自适应。

## 针对EPG显示的乱码问题

根据ETSI EN 300 468国际标准，所有的EPG以及Service Name的名字都会按照DVB多国语言的标准进行编码，但根据之前方案的经历，会出现很多的DTMB标准以及部分DVB-S标准的卫星或者TP上出现非标准的情况(即无法查到这个first byte对应的标准)。

根据码流读入first byte或者second byte、third byte与表对比，是否符合客户要求的相应语言要求：

![](./images/dvb_iso0.png)

![](./images/dvb_iso1.png)

**其中没有ISO 8859-12标准，ISO 8859-12标准的“坑”之前被作为梵语天城体的显示，后来不知道怎么的被“莫名其妙”地下架了。**

针对非标准情况，处理步骤如下(若不符合，或在保留字段内直接进行转换)：

```cpp

if(... 符合某些非标情况)
{
    gdi_encoding_convert("iso6937", "iso8859-09"); // 凡是first byte大于等于0x20的非标情况均可认为是ISO6937标准，此接口将标准ISO6937按ISO8859-09处理
    gxgdi_iconv(src, &dst, src_len, &dst_len, NULL);
    gdi_encoding_convert("iso6937", NULL); // 必须恢复标准ISO6937处理，不恢复，则后果自负

    // 针对这类非标处理，dst是gxgdi_iconv函数开出来的内存空间，应用必须在使用后自行释放，否则会有内存泄漏。
}

```

## 各标准简介

### ISO/IEC 10646

即UCS2，用两个字节表示一个文字，如编码为0x6E的，会表示为0x00、0x6E。由于存在0x00的可能，所以不能用strlen、strcat、strcmp等一系列接口函数。由于两个字节表示，所以码值小于等于0xFFFF的都能表示，可以去UNICODE码表查询(UNICODE可以表示所有字符)。

### ISO 6937

主要是一些欧洲文字，可以用拼接的办法表示一个欧洲的EPG文字。由于较早开发，所以标准相对较老，可以表示的国家存在一些欠缺，所以很难准确地说哪些国家使用ISO 6937标准，其没哟first byte。

### UTF8

只要字库是全的（当然字库全是一种理想状态），就能表示全球所有文字。即解析要用对应的标准去做，而解析出来的字符都可以在utf8中找到对应字符用于显示。

而UTF8可以认为是UNICODE的一种变种，目的其实是可以使用经典的字符串接口：strcat、strlen和strcpy等。

|       Unicode符号范围(hex)      |          UTF-8编码方式(binary)          |
|---------------------------------|-----------------------------------------|
| 0x00000000 - 0x0000007F         |     0xxxxxxx                            |
| 0x00000080 - 0x000007FF         |     110xxxxx 10xxxxxx                   |
| 0x00000800 - 0x0000FFFF         |     1110xxxx 10xxxxxx 10xxxxxx          |
| 0x00010000 - 0x0010FFFF         |     11110xxx 10xxxxxx 10xxxxxx 10xxxxxx |


### GB2312/GBK

GBK全称《汉字内码扩展规范》。中华人民共和国全国信息技术标准化技术委员会1995年12月1日制订，使用了双字节编码方案，其编码范围从8140至FEFE，共23940个码位，共收录了21003个汉字。

### BIG5

由台湾财团法人信息产业策进会为五大中文套装软件所设计的中文共通内码，在1983年12月完成公告。又称为大五码或五大码，是使用繁体中文（正体中文）社区中最常用的电脑汉字字符集标准，共收录13,060个汉字。

### KSX

韩国使用的韩语编码标准。

## 两种不同的GB2312实现

有两种不同的GB2312实现，主要是编码方面，在它们之间存在少量的差别，其中至少有一个是错误的。
字节序 实现A 实现

A1A4 U+00B7 MIDDLE DOT U+30FB KATAKANA MIDDLE DOT

A1AA U+2014 EM DASH U+2015 HORIZONTAL BAR

实现A与GBK/GB18030兼容，实现B则不兼容。
在2015年， 微软.Net Framework在使用实现A。 iconv-1.14， php-5.6， ActivePerl-5.20， Java 1.7， Python 3.4在使用实现B。

从视觉上来看，实现A与实现B并无差别，其中0xA1A4是点号，0xA1AA是-号。

考虑到兼容性，GXGUI标准实现的是A标准。

## 历史遗留原因，键值有可能需要取反

## 问题产生

某项目从客户那里得到一把遥控器与一份遥控键值图。

![](./images/1878571803.jpg)

以“向上”键为例，按图中所示的(Customer code)(0xBF) + (Key value)，应该是0xBF15。

而我们方案读取出来的键值是：

```
---->[key1]:code = 0xff0257a8.

---->[key2]:syscode = 0xff,usercode=0x57.

---->[key-reverse]:syscode = 0x2,usercode=0xa8.
```

每一个值都与客户的键值挨不上边，而客户反映是他们拿了竞争对手（阿里、M-Star）读取出来的键值全都是0xBF15。

经过红外驱动工程师仔细分析，得出结果：

**驱动中，我们键值的脉冲读取顺序与客户的脉冲读取顺序正好相反。且我们将键值的高16位再取反了。**

|        |        hex        |      binary           |            reverse-binary        |    reverse-hex    |
|--------|-------------------|-----------------------|----------------------------------|-------------------|
|syscode0|     0xFF          |1111 1111(取反:0000 0000)  |    0000 0000                 |    0x00           |
|syscode1|     0x02          |0000 0010(取反:1111 1101)  |    1011 1111                 |    0xBF           |
|syscode2|     0x57          |0101 0111                  |    1110 1010                 |    0xEA           |
|usrcode |     0xA8          |1010 1000                  |    0001 0101                 |    0x15           |

## 解决方法

针对此问题，主要原因如下：

我们公司红外驱动的解析部分，自公司有红外驱动以来，一直都是如此解析的。至于方案中见到竞争对手M-Star与阿里都与我们不同，既然两家都一样与我们不同，也许是我们一开始就将红外驱动的脉冲解析部分写错了。不过到底是谁对谁错，已经不重要了，红外驱动已经不可能为某一个或几个方案做出修改，而影响公司数百个项目。不然到时候新版本一升级，就会到处报“死机”，到头来大家在各自的XML中改键值，无效工作量不是一般地大。

所以，我们已经意识到这类问题，对于这类方案遇到的问题，如果客户非常纠结键值的统一性只能按上述方式反转了。至于SDK项目，所有的键值都是被keymap.xml透明的，所以无论正读、反读都无所谓，不会对方案结果产生影响。

# 为什么不能多线程调用GUI接口

GUI服务与其他PM服务、Player服务、EPG服务等服务一样是挂载在bus下的服务，需要多任务的操作必须通过bus传递消息实现。

多线程操作GUI所带来的问题：

## 死机

以字符串设置为例，设置一个新的字符串会导致之前的字符串释放，而如果正好之前的字符串正在使用，则会导致访问了错误内存而造成程序崩溃。

![](./images/ca1.jpg)

## 界面出现乱象

另一个线程触发了一些绘制操作，导致GUI的绘制出现“不存在”的信息，很难查找。

## 死锁

GUI本身有一些锁，随意些自身由于Console线程和Message线程的资源互斥访问而加上的锁，会导致应用死锁。

比如：

![](./images/ca2.jpg)

## 获取数据错误

当GUI需要调用GUI_GetProperty函数获取数据，而另一个线程或是GUI主线程会修改数据，就很容易造成读脏数据的可能。

**所以，GUI接口不允许多线程操作。如有其他线程需要完成绘制操作，则通过向GUI主线程发送消息完成。**

# 字库

一般情况，针对高清方案都建议选择矢量字；标清方案建议选择点阵字。但针对如MINI GUI或者特殊情况的方案，需要根据矢量字和点阵字的特殊情况考虑：

## 内存占有量

- 点阵字

	**内存占有量 = ∑{[(字宽度 / 8) + if(字宽度 % 8)] × 字高度}**

	比如：收录了600个字，每个字都是24 × 24的，那就是总内存量 = 600 × 24 × 24 / 8 = 43200 = 42K。

	flash的占用量和内存占用量一样。

- 矢量字

	**最大内存占有量 = ∑(ASCII码字宽度 × ASCII码字高度) + MAX[∑(i = 0; i < 256)(非ASCII码字宽度 × 非ASCII码字高度)]**

	flash占用量等于ttf的文件大小。

**所以，中文使用ttf文件矢量字库需要慎重考虑，因为中文矢量字库都很大。另一方面，中日韩文字基本是横平竖直的，从以下美观程度考虑，点阵字的缺陷很难体现。**

## 美观程度

- 点阵字

	在标准清晰度电视方案中与矢量字差别不大，在高清晰度电视方案中，与矢量字差别较大。其美观程度大不如矢量字。

- 矢量字

	在高清晰度电视方案中，矢量字显示非常美观，且文字越大越美观。

## 是否可调整大小

- 点阵字

	不能

- 矢量字

	能

## 是否可在每个界面都使用

- 点阵字

	每个界面都可以使用，因为开机后点阵字的信息都导入到了内存中。

- 矢量字

	升级界面不要使用，因为矢量字开机时不是所有信息都导入内存的，有部分信息会去读文件。那么在升级界面使用矢量字，会造成读文件。然而，此时由于升级，矢量字区域正好已经擦除，故有可能会出错。

## 显示速度

- 点阵字

	快，几乎没有感觉。

- 矢量字

	显示ASCII码是比较快的，因为事先已经将信息导入。但切换语言到一个新文字区域，会重新导入，会暂时比较慢。然而，针对中文、韩文以及日文这些字形较多的文字来说，显示会明显比较慢，因为需要不同区域经常导入，暂时无法解决此问题。

## 是否可在各种颜色格式的方案中使用

- 点阵字

	可以

- 矢量字

	位色不能显示

方案使用矢量字库显得文字边缘非常光滑、漂亮，使用点阵字库显得边缘噪点非常多，不是那么美观。

造成这样差别的原因是矢量字从文字颜色到背景色有一层渐变过渡，使得用户感觉视觉上和平滑。其实是有过渡色的，只是过渡色“欺骗”了双眼。

过渡色必须过渡得好，不然会造成比点阵字更不美观的颜色。过渡色是渐变的，由《GUI常见问题（二）——颜色篇》中可知就32位色和16位色在渐变色上存在差异。

不过16位色的差异在矢量字过渡色上还是不容易用肉眼分辨的。但是8位色只有256种颜色与16位色65535种颜色差别很大。

**所以8位索引色很难渐变过渡，故8为索引色方案不能适用矢量字库。**

## 为何在RGB565方案的OSD透明色上显示矢量字，会长毛

现象 ： 在32bpp方案上矢量字显示正常；

在16bpp方案上矢量字会“长毛”。 如图上面为16bpp效果下面是32bpp效果

透明底色 ：

![](./images/font_display1.png)

非透明底色：

![](./images/font_display2.png)

ARGB8888有8位的阿尔法通道,支持透明色，RGB565则不支持；

RGB565由于没有透明通道，在透明处理上，采用指定Color Key的办法。矢量字的过渡色，是以Color Key颜色的原色过渡的，在字形弯曲处采用渐变的方式但还是有颜色差别的，只是在非透明底色上被底色掩盖，人眼看不出来。

**所以，建议在RGB565方案中尽量不要在透明色上绘制矢量字**
